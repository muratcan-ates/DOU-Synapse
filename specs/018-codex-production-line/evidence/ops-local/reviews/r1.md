# OPS1 R1 — independent review of the measured statement-error boundary

Reviewed 8 September 2026. This review only read existing receipts, source and test text and computed file hashes. It ran no database, test, server or Git operation and changed no repository file.

## Decision

The characterization is valid and closes the previously unmeasured R1 behavior for the current read-only admin overview on the measured stack. The helper **does leave its supplied PostgreSQL transaction unusable after a caught statement error**. Nevertheless, the actual admin request completes with HTTP 200 and a degraded overview; its separately committed allowed audit remains visible, and the following public readiness request succeeds in a clean logical session. This is measured behavior, not an HTTP-200 assertion manufactured by the test.

No mandatory SAVEPOINT change is justified for this terminal read-only caller by this experiment alone. Preserve and document the limited caller contract. Do not describe the helper as restoring a supplied transaction or approve its reuse inside write-bearing work on the strength of this result. There is no measured audit loss or user-data loss in this route.

## Recommended narrowly stated contract

The only current callers are `app/api/admin.py:38`, which supplies the already-authorized terminal read-only overview session, and `app/api/health.py:32`, which lets the checker own an independent session. The catch is `app/core/readiness.py:51–56`; it records degraded state without repairing the supplied transaction. The audit transaction is already completed in `app/api/deps.py:220–224`, before the overview handler.

Suggested documentation wording:

> A supplied-session readiness probe can return degraded after a SQL statement error while leaving that PostgreSQL transaction failed. The current admin caller only reads its overview before probing and performs no further production queries or writes afterward. On the measured local stack, this terminal read-only path returned a degraded overview, preserved the independently committed access audit, and the next public probe used a clean session. The helper does not recover a supplied transaction and must not be treated as a general-purpose safe probe inside write-bearing work.

Keep the original observations and paired healthy control. A small durable regression may later codify the deliberately chosen read-only HTTP/audit contract; it must retain the real SQL error and separate audit read. If future work needs successful queries/writes after the probe, make that a separate change with a real write-and-rollback regression and a properly scoped savepoint or separate-session design. Do not add a rollback/commit that takes ownership of the caller's whole transaction or borrow another main-pool connection while holding the first one.

## What this does not establish

The result covers an ordinary SQL statement error on a still-connected PostgreSQL session. It does not establish behavior for socket loss, driver invalidation, pool exhaustion, timeouts, cancellation or failure during COMMIT. It does not measure a PostgreSQL COMMIT command tag and therefore must not be worded as proof that the failed main transaction committed. SQLAlchemy `in_transaction=true` was observed before dependency exit; that flag does not establish that PostgreSQL can still execute statements—the actual 25P02 proves the opposite in this case.

The current main route has no writes to lose. A caught error in a future transaction containing writes could have different finalization/data-loss implications; no general safety guarantee for that case follows. The independently persisted audit proves only this audit boundary, not that arbitrary writes in the failed main transaction survive. Logical-session cleanliness does not prove the next request used the same physical backend or that every pool connection was exercised. No real provider, embedding warmup, legal compliance, production deployment or all-failure readiness guarantee is claimed.
