## 3. Quiescence ve gerçekten beklenen süreç

`e2e_audit_guard.py:184–203` yalnız root'un yazdığı JSON'u doğruluyor: run, target, pozitif PID, stopped, exact integer exit0 ve Playwright sonucu. **Guard process wait yapmıyor; bu alanları yazarak gerçek kapanış ispatlanmaz.** Henüz bulunmayan parent adaptörü güven üreticisidir.

Root'un dar sözleşmesi:

1. API'yi aynı parent'ın doğrudan Popen child'ı olarak çalıştır; yalnız shell/`uv run` wrapper'ının bitmesini gerçek sunucu çıkışı sayma. Reload veya birden fazla worker varsa ana PID'nin bitişi yeterli olmayabilir. Bu kabul için doğrudan tek worker, reload kapalı, beklenen kaynak/runtime ve açık process kaydı en dar yoldur.
2. Ready kapısı yalnız çalışan mevcut bir porta HTTP200 geldiği için geçmemeli. Child'ın yaşadığı ve kendisine ait dinleme noktasını açtığı doğrulanmalı; port çakışmasında başka API'ye bağlanıp testlere devam edilmemeli. Önceden sahip olunan socket veya başarılı bind + child yaşam döngüsü bağı kullanılabilir.
3. Playwright başarılı veya başarısız bittikten sonra yalnız bu API child'ını durdur; gerçek wait sonucunu al. Başlatma/ready hatası veya timeout varsa üst sonuç başarısız kalmalı. Guard'ın sonradan PASS olması önceki evre hatasını silemez.
4. Guard şu anda `ownedApiExitCode == 0` istiyor. Gerçek runtime'ın normal SIGTERM dönüşü `-15` veya başka bir kodsa onu 0 diye yeniden etiketleme. Doğrudan uygulanan shutdown yolunu ölç; gerekirse clean shutdown semantiğini ayrı kanıtla ve guard sözleşmesini kontrollü değiştir. SIGKILL, timeout ve belirsiz kapanış clean-stop olmaz.
5. Guard'ın varsayılan PLAN evresi exit0 döner (`:143–145`). Parent yalnız exit code'a bakmamalı: begin için `BEGIN_RECORDED` ve yeni beklenen dosyalar; finish için yeni final-accounting, doğru scope, `PASS` ve exit0 birlikte şart olmalı. Mevcut veya eski PASS dosyasıyla başarısız yeni çağrıyı kapatma.

API kapanışı sonrası audit commit yapan bağımsız başka API süreçleri varsa bu normal kabulün exclusive hedef varsayımı bozulur. Başka servisi process adı/port taramasıyla öldürmek çözüm değildir.

## Root için en dar gerçek kabul sırası

1. Adaptör hazır olduktan sonra yeni hedef/port ve private passfile/pins ile guard begin gerçek SQL; yanlış cluster/OID/rol/endpoint negatiflerinde sentinel/API/DELETE0.
2. Doğru targetId olsa bile yanlış cleanup PG veya API DSN yönlendirmesi reddi; eski web server'ın kullanılamaması. Guard A temiz kaldı diye yanlış B yazımı kabul edilmemeli.
3. Protected baseline satırı + gerçek audited istek → exact receipt cleanup → own API gerçek wait → finish PASS. Kaynak hashleri önce/sonra sabit ve tam zinciri kapsamalı.
4. Collector atlanan committed istek → finish FAIL ve yeni satır yerinde; baseline içerik değişimi/silinmesi → COUNT aynı veya yeni satır0 olsa da FAIL.
5. İki interleaved run ile A cleanup sonrası protected+B tam fingerprint eşitliği; normal finish'i B satırlarını yok sayacak biçimde gevşetme.
6. Yanıt kaybı/incomplete session, Bun nonzero, startup/ready/stop timeout, eksik makbuz ve PLAN-only yanlış çağrı → üst sonuç başarısız. Hiçbir geniş silme veya exit kodunu yeniden etiketleme yok.

Bu inceleme, adayın bütünleşik runtime/SQL/CI kabulü yerine geçmez. Root yaşam döngüsü adaptörü açık iş olarak kalır.
